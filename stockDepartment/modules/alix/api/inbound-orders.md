# Приход товара — интеграция 1С ↔ Nomadex (WMS)

**Base URL:** `https://alix-demo-wms.nmdx.kz`

Полный URL эндпоинта: `https://alix-demo-wms.nmdx.kz/alix/api/v1/inbound/orders`

Процесс:

1. **1С → WMS.** 1С отправляет документ приёмки в WMS через POST.
2. **Внутри WMS.** Оператор склада сканирует каждую единицу товара и подтверждает приёмку.
3. **WMS → 1С.** На ключевых событиях WMS уведомляет 1С о смене статуса:
   - первое сканирование → `in_work`
   - подтверждение приёмки → `completed` / `completed_with_differences`

## POST /alix/api/v1/inbound/orders

Создаёт документ приёмки («Поступление ТМЗ»).

### Запрос

**Method:** `POST`
**Content-Type:** `application/json`

```json
{
  "order_id": "TEST-INB-003",
  "1с_uuid": "test-uuid-inbound-003",
  "comment": "Тестовая накладная",
  "items": [
    {
      "barcode":  "8682538209166",
      "article":  "1100005014",
      "quantity": 1
    }
  ]
}
```

### Поля запроса

| Поле                 | Тип     | Обязательное | Описание |
|----------------------|---------|:------------:|----------|
| `order_id`           | string  | да           | Номер документа «Поступление ТМЗ» в 1С. |
| `1с_uuid`            | string  | да           | UUID документа в 1С. Используется для связи: во всех последующих уведомлениях WMS вернёт этот же идентификатор. |
| `comment`            | string  | нет          | Произвольный комментарий. |
| `items[].barcode`    | string  | да           | Штрих-код товара. По нему сканер на складе идентифицирует позицию. |
| `items[].article`    | string  | да           | Артикул товара (SKU в 1С). |
| `items[].quantity`   | int     | да           | Ожидаемое количество. |
| `items[].guid`       | string  | нет          | GUID товара в 1С. Если не передан — WMS сам найдёт карточку по `barcode`, далее по `article`. |
| `items[].datamatrix` | array   | нет          | Data Matrix-коды в формате base64, если требуется посерийный учёт. |

> **Как WMS резолвит карточку товара.** Приоритет: `guid` → `barcode` → `article`.
> Для надёжного резолва достаточно `barcode` — он уникален в мастер-данных Nomadex.
> `article` — fallback, если штрих-кода нет в синхронизированной номенклатуре.

### Успешный ответ (200)

```json
{
  "status":  "success",
  "message": "",
  "code":    "",
  "wms_id":  123
}
```

`wms_id` — внутренний ID документа в Nomadex, возвращается в уведомлениях о смене статуса.

### Ошибка валидации (400)

```json
{
  "status":  "error",
  "message": "Не заполнен order_id или items",
  "code":    "",
  "wms_id":  ""
}
```

Возможные сообщения:

| message | Причина |
|---------|---------|
| `Не заполнен order_id или items` | Отсутствует `order_id` и/или `items`. |
| `Пустой order_id` | `order_id` пустой. |
| `Не заполнен 1с_uuid` | Отсутствует поле `1с_uuid`. |
| `Пустой 1с_uuid` | `1с_uuid` пустой. |
| `Пустой items, нет товаров` | `items` не содержит позиций. |
| `Такая накладная уже есть, она в работе` | Документ с таким `1с_uuid` уже принят в сканирование или завершён (см. [Повторная отправка](#повторная-отправка)). |

## Уведомления о смене статуса (WMS → 1С)

На ключевых событиях WMS отправляет POST в 1С.

**URL эндпоинта в 1С:** `POST {1С_BASE_URL}/ChangeDocumentStatus/`

Один эндпоинт обслуживает все переходы статусов: `in_work`, `completed`, `completed_with_differences`.

### Payload

```json
{
  "order":  "inbound",
  "wms_id": "123",
  "status": "in_work"
}
```

| Поле     | Тип    | Описание |
|----------|--------|----------|
| `order`  | string | Тип документа. Для приёмки всегда `inbound`. |
| `wms_id` | string | Внутренний ID документа в Nomadex (то, что вернулось в `wms_id` при создании). |
| `status` | string | Новый статус. Допустимые значения: `new`, `in_work`, `completed`, `completed_with_differences`, `shipped`. |

### Когда WMS шлёт уведомления

| Событие в WMS | Отправляемый `status` |
|---------------|-----------------------|
| Первое сканирование товара в документе | `in_work` |
| Подтверждение приёмки, фактическое кол-во = ожидаемому | `completed` |
| Подтверждение приёмки, фактическое кол-во ≠ ожидаемому | `completed_with_differences` |

### Ожидаемый ответ от 1С

- `HTTP 200 OK` — уведомление принято.
- Любой другой HTTP-код или сетевая ошибка — WMS логирует, но сканирование и подтверждение продолжают работать. Приёмка на складе **не блокируется** недоступностью 1С.

## Жизненный цикл документа

Статусы документа внутри Nomadex:

| Код | Название | Описание |
|:---:|----------|----------|
| 1   | NEW      | Документ создан через API, ожидает приёмки на складе. |
| 3   | SCANNING | Начато сканирование (как минимум одна единица товара). При переходе в этот статус WMS шлёт в 1С `in_work`. |
| 4   | SCANNED  | Все позиции по накладной отсканированы. Ждёт подтверждения оператора. |
| 9   | CONFIRM  | Приёмка подтверждена, товары доступны на складе. При переходе в этот статус WMS шлёт в 1С `completed` или `completed_with_differences`. |

## Повторная отправка

Поведение при повторной POST-отправке документа с тем же `1с_uuid`:

| Текущий статус документа в WMS | Поведение |
|--------------------------------|-----------|
| NEW (не начинали сканировать)  | WMS удаляет старые позиции и создаёт заново — перезапись. |
| SCANNING / SCANNED / CONFIRM   | Возвращается `400` с `message = "Такая накладная уже есть, она в работе"`. |

Соответственно повторно отправлять накладную безопасно **только** пока на склад ещё не начали её сканировать.
